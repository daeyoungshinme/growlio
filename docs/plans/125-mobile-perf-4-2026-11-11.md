# 모바일 체감 성능 4차 개선 계획 (docs/plans/125, 2026-11-11)

## Context
사용자 요청: "모바일에서 쓰기 편하도록 전반적인 성능 개선". 계획 72(10-25)에서 부팅·인증·번들·백엔드 1차 병목을 처리했다. 그 뒤 약 250커밋(전술·지수그룹·주문취소·지금할일·환전계획·기간별매수 등)이 들어오면서 새 병목이 생겼다. 3갈래(프론트 부팅·렌더 / 데이터 요청 흐름 / 백엔드 지연)로 코드를 읽었다. 측정은 하지 않았다(실데이터·실기기 없음). 아래 항목은 코드로 근거를 확인한 것만 넣었다.

핵심 축 3가지:
1. **백엔드가 외부 HTTP를 기다리는 동안 DB 커넥션을 쥔다.** 환전계획 풀 고갈(#260)과 같은 패턴이 홈 경로 6곳에 남아 있다. 풀은 5+2이고 0.1 CPU다.
2. **콜드 스타트에 홈이 비어 보인다.** persist된 쿼리가 gcTime 30분에 지워진다. 지금할일·챌린지는 persist되지 않는다. BottomNav 배지가 무거운 drift 계산을 따로 한 번 더 부른다.
3. **스크롤·당겨서 새로고침 중 버벅임.** 비패시브 touchmove 리스너, 매 프레임 바뀌는 context value 때문이다. 모바일에서 숨긴 차트·모달이 recharts·zod를 끌어온다.

산출물: 이 내용을 `docs/plans/125-mobile-perf-4-2026-11-11.md`로 저장하고 `docs/plans/README.md`에 행을 추가한다. 브랜치는 `perf/mobile-perf-4`, PR 1개, Phase별 커밋.

## Phase A — 백엔드: 외부 I/O 중 커넥션 반납·음성 캐시 (High)
패턴: 외부 호출 직전에 `await db.commit()`. `AsyncSessionLocal(expire_on_commit=False)`이고 다음 쿼리는 새로 autobegin한다. 3a83141b의 환전계획 수정과 같은 방식이다.
- **A1 배당 체인** `services/dividend/orchestrator.py:326-334`: `_fetch_estimated_dividend_map` 전에 commit. `get_position_dividend_yields`(`:355-362`)도 같게. `/dashboard` 콜드 경로.
- **A2 무배당 종목 음성 캐시** `services/dividend/fetcher.py:303-306`: 지금은 `dps==0 and yield==0`이면 캐시하지 않아 성장주·TR ETF·금이 매번 7개 소스를 다시 탄다. `_fetch_from_network`가 "소스 하나라도 정상 응답"을 반환하게 하고, 그 경우 `{dps:0, yield_decimal:0}`을 `TTL_DIVIDEND_INFO`로 캐시한다. 전부 실패면 짧은 TTL(10분)만. 읽는 쪽(`:270` 근처 캐시 히트 판정)이 0값 캐시를 히트로 인정하는지 확인한다.
- **A3 해외 실현손익** `services/tax/overseas_realized_service.py:381-391`: 계좌 루프를 둘로 나눈다. 먼저 자격증명·토큰(DB)을 직렬로 모으고 commit한다. 그다음 KIS 호출을 `asyncio.gather`로 병렬 실행한다(계좌별 예외 격리 유지). 함수 전체를 기존 `utils/inproc_lock`의 `single_flight_fetch`로 감싸 action-items와 insights의 동시 호출을 1회로 줄인다. `cache_invalidation.py:220-226`에서 `tax:overseas_realized` 무효화는 `positions_changed`일 때만 한다.
- **A4 리스크 지표** `services/risk_service.py:120-172`: `query_latest_position_map` 후 commit한다. bare `run_in_executor`를 `run_yf_bounded`로 바꾼다. O(N²×252) 상관 루프(`:58-102`)는 executor 함수 안으로 옮긴다(가능하면 numpy). `cache_invalidation.py:204`의 `risk_key` 무효화는 `positions_changed`일 때만 한다.
- **A5 analyze** `services/rebalancing/portfolio_analysis_service.py:71-128`: `returns_task`를 overview 직후 시작한다. KIS/DART 자격증명·설정을 먼저 읽고 commit한 뒤, `collect_dividend_map`·가격 보강·`fetch_market_and_risk_signal`을 `gather`한다. 가격 보강의 KIS 폴백(`price_service.py:233`)이 `db`를 쓰면 짧은 자체 세션으로 바꾼다.
- **A6 기타 동일 패턴**: 아래 세 곳에서 외부 호출 전에 commit한다.
  - `challenge_service.py:235-238`(대시보드 single-flight 대기 전). DEPOSIT 챌린지 N+1도 1쿼리로 묶는다.
  - `index_exposure_service.py:136-141`(ETF 프로필 조회 전)
  - `api/v1/tactical.py` → `market_signal_service.get_market_signal` 전

## Phase C — 프론트: 콜드 스타트에 바로 보이게 (High)
- **C1 gcTime ≥ maxAge** `main.tsx:33`: 전역 기본 `gcTime`을 `STALE_TIME.DAY`로 올린다. TanStack 문서상 persist는 gcTime ≥ maxAge(24h)를 요구한다. 지금은 30분 동안 관찰자가 없으면 홈 캐시가 저장소에서 사라진다.
- **C2 persist 확대** `constants/queryConfig.ts:14-21`: `action-items`·`challenges`·`portfolios`·`market-signal`·`exchange-rate`를 추가하고 `PERSIST_CACHE_BUSTER`를 올린다. persist 크기 증가를 막기 위해 `goal-recommendation`은 `overall` 변형만 남긴다(키 2번째 요소로 판정).
- **C3 프리페치 조기화**: `App.tsx:117-125`는 Supabase SDK 로드를 기다린 뒤에야 `prefetchDashboardData`를 호출한다. `storedSession.readValidStoredToken()`이 유효하면 `PersistQueryClientProvider onSuccess`(복원 직후)에서 바로 호출한다. `api/prefetch.ts`에서 쓰이지 않는 `settings`는 빼고 `action-items`·`challenges`를 넣는다.
- **C4 BottomNav 배지** `components/layout/BottomNav.tsx:10-28`: 리밸런싱 배지를 action-items의 REBALANCE 항목에서 파생한다. 구현 전에 `action_items_service`의 REBALANCE 조건이 `drift_summary.needs_rebalancing`과 같은지 확인한다. 같지 않으면 대안으로 drift 쿼리를 `staleTime 5분` + `/rebalancing` 경로에서만 enabled하고, 그 외 경로에서는 캐시만 읽는다. 챌린지 배지도 action-items의 CHALLENGE 항목으로 대체할 수 있는지 같은 방식으로 확인한다.
- **C5 지금할일 staleTime** `ActionItemsCard.tsx:169-173`: MEDIUM → 5분. 관련 mutation이 이미 정밀하게 무효화한다.
- **C6 챌린지 카드 깜빡임** `DashboardPage.tsx:174-180`: `useChallenges().isLoading`일 때 빈 상태 카드 대신 스켈레톤을 보여준다.
- **C7 콜드 서버 재시도 폭주** `main.tsx:32`: `retry`를 함수로 바꿔 4xx에서는 재시도하지 않게 한다. 네트워크 오류·5xx·timeout만 1회 재시도하고 지수 백오프를 둔다.

## Phase D — 프론트: 무효화 폭주 정리 (Med)

- **D3 계좌 생성 2중 폭주** `useAccountMutations.ts:35,43`: sync 전에는 `accounts`만 무효화하고, 폭주성 무효화는 sync 후 1회만 한다.
