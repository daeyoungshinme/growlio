# 27. 리밸런싱 실행 파이프라인 — 잔여 로드맵 (2026-08-14 감사)

2026-08-14, "리밸런싱 탭 검토 후 개선 계획"이라는 요청에 대해 — 이 탭은 이미 20회 이상(페르소나별/요구사항완결성/성능/접근성/보안/실기기 테스트/경쟁앱 비교 등) 감사되어 UX·기능 완결성 관점은 사실상 소진된 상태였음을 확인하고, 사용자 선택으로 처음 다뤄보는 축(AUTO 실행 파이프라인의 동시성/장애복원력, 드리프트·게이트 계산의 수치 정확성)으로 3개 서브에이전트 조사를 진행했다.

발견된 문제 중 **매수 leg 중복실행 가능성**(`execute_due_buy_legs`의 클레임 가드에 `token_consumed_at` 체크 누락), **게이트 판정과 실제 체결이 서로 다른 시점 데이터를 사용**(라이브 시세 반영이 세금/한도 게이트 이후에 일어나던 순서 문제), **마이너스 예수금이 컴포넌트 단위로 조용히 0 클램프되던 버그**, **하루 합산 거래한도 체크의 AUTO잡-수동실행 간 레이스**는 같은 세션에 구현 완료했다(상세는 `plan_service.py`/`order_builder.py`/`service.py` diff 및 관련 테스트 참고 — 백엔드 2048 tests 88.05%, 프론트 1454 tests, ruff/mypy/tsc/eslint 전부 클린).

이 문서는 손이 많이 가거나(브로커 API 조사 필요) 실거래 리스크가 커서(2-leg 실행 흐름 재설계) **이번 세션 범위에서 제외하고 다음 세션으로 이관**하는 항목만 기록한다.

## 이관 항목

### 1. 브로커 호출 실패 시 재조회/멱등성 부재
`_order_executor_common.py:41-81`(`execute_single_order`)과 `plan_service.py`의 `_execute_leg`(819-857)는 KIS/키움 주문 API 호출이 타임아웃/예외를 던지면 무조건 `FAILED`로 마킹하고 끝난다 — 응답만 유실됐을 뿐 실제로는 브로커에 주문이 접수됐을 가능성(흔한 브로커 API 패턴)을 재조회로 확인하는 로직이 없다. 다음 세션에서 다룰 경우:
- KIS/키움 API에 멱등키(idempotency key) 또는 클라이언트 주문번호 지정 기능이 있는지부터 공식 문서/기존 오픈소스 클라이언트 조사 필요(`docs/plans/20` 5번의 API-ID 조사와 유사한 리서치 선행 작업).
- 없다면 "타임아웃 시 브로커 잔고/미체결 주문 조회로 실제 접수 여부 확인" 폴백을 검토.

### 2. 매도/매수 2-leg 부분 실행 시 복구·가시성 부재
SELL(승인 필요)/BUY(대기 후 자동)는 독립된 생명주기를 가진다(`plan_service.py` 상단 docstring). 한쪽 leg만 성공하고 다른 쪽이 실패해도 자동 재시도나 "반쪽 실행된 플랜" 조회 화면이 없다 — 사용자는 실패 이메일(`_notify_leg_execution_failed`)로만 인지하고 나머지는 이력 탭에서 직접 대조해야 한다. 다음 세션 착수 시:
- 최소 범위: 이력 탭에서 같은 `plan_id`의 leg들을 묶어 "부분 실행됨" 배지로 노출하는 조회 전용 개선부터 검토(실행 로직 변경 없음, 리스크 낮음).
- 확장 범위(리스크 높음): 실패한 leg의 자동 재시도 — 별도 세션에서 신중히 설계.

### 3. 매수 leg도 매도처럼 실행 직전 잔고 clamp 적용
매도는 `_execute_sells_with_clamp`로 실행 직전 실시간 잔고에 맞춰 수량을 clamp하는 안전장치가 있으나, 매수는 대응 로직이 없다 — `buy_wait_minutes`(최소 1분) 대기 중 예수금이 줄었을 가능성(다른 자동 매수 leg 선체결, 수동 출금 등)을 반영하지 못한다. 이번 세션에 매수 수량 자체를 라이브 가격 기준으로 재계산하도록 고쳤지만(`refresh_live_prices`), 이는 "가격" 변화 대응이지 "가용 잔고" 변화 대응은 아니다 — 별개 안전장치로 다음 세션에서 검토.

### 4. `plan_service.py` 999줄 → 더 커짐
`docs/plans/24`(2026-07-29) 2번에서 이미 "실거래 경로라 회귀 위험 큼"으로 이관된 파일. 이번 세션에서 게이트 순서 재정렬(refresh_live_prices 이동)과 하루한도 락(inproc_lock) 적용으로 볼륨이 소폭 더 늘었다. `goal_recommendation_service.py`가 1622줄에서 분리된 전례(`docs/plans/26`)처럼 계획생성/게이트판정/leg실행 3책임 분리를 검토할 것 — 단, 이번 세션에 이 파일의 실행 로직 자체를 다수 변경했으므로, 분리 작업은 최소 한 릴리스 이상 안정화 기간을 두고 별도 세션에서 진행 권장.

## 이번 세션에서 조사했으나 "실제 버그 아님"으로 결론 내린 항목 (참고용, 재작업 대상 아님)

- **`shares_to_trade` 계산의 `int()` 절삭 vs `math.floor()` 불일치** — 최초 조사에서 "지점마다 절삭 방식이 다르다"는 의심이 있었으나, 실제로 뜯어보니 `order_builder.py`의 `abs(int(item.shares_to_trade))`(0 방향 절삭)가 **의도적으로 올바른 선택**이었다: 마이너스(매도) 방향의 소수 수량을 `math.floor()`로 바꾸면 목표 대비 더 많이 매도해(예: -7.3주 → floor는 -8주, int는 -7주) 오히려 목표를 초과 매도하게 된다. 국내 정수 보유 종목엔 애초에 영향 없고, 해외 소수 보유(드문 케이스)에서도 현재 방식이 "목표를 넘지 않는" 안전한 쪽이라 변경하지 않았다.
