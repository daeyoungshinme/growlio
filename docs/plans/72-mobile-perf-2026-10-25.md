# 모바일 체감 속도 개선 계획 (2026-10-25)

## Context
사용자가 "모바일에서 전반적으로 느리다"고 보고. 이전 라운드(09-12 번들/supabase 지연로드, 09-17 대시보드 세션 동시성·DCA 캐시, 10-22/23 목표조정 SWR)의 수정은 회귀 없이 유지됨을 확인했다(dist modulepreload에 vendor-charts/dnd/supabase 없음).
이번 조사(프론트 부팅·프론트 런타임·백엔드 3갈래)에서 새 병목을 찾았다. 가장 큰 축은 세 가지다.
1. **콜드 스타트 인증 경로**: 토큰 없이 요청 → 401 → refreshSession → 재시도. 또 30분 지나면 전체 화면 스피너가 뜬다.
2. **앱 resume/탭 진입 시 요청 폭주 + 외부 API 동기 대기**: drift-summary/action-items가 FRED·yfinance·KIS를 타고, DB 커넥션 7개를 외부 I/O 동안 점유한다.
3. **무거운 작업이 이벤트 루프·마운트 경로에 있음**: 전술 백테스트 simulate 동기 실행, 리밸런싱 포트폴리오 탭 진입마다 브로커 실시간 잔고 조회.

실측 데이터가 없으므로(로컬에 실데이터 없음) Phase 0에서 계측을 먼저 깔고, 나머지는 **근거가 코드로 확정된 것만** 수정한다.
산출물은 프로젝트 관례대로 `docs/plans/72-mobile-perf-2026-10-25.md`로 저장하고 `docs/plans/README.md` 인덱스에 행을 추가한다.

> 작업 트리에 다른 세션의 미커밋 변경(plans/71 등)이 있다. 겹치는 파일(`queryInvalidation.ts`, `useTacticalAllocation.ts`, `tactical.py`)은 수정 전에 `git diff`로 확인하고, 그 변경을 되돌리지 않는다.

## Phase 0 — 계측 (저위험, 먼저)
- `backend/app/main.py:129` `_path_prefix`: Prometheus 라벨이 4세그먼트에서 잘려 `/dashboard`와 `/dashboard/action-items`가 합쳐진다. 라우트 템플릿(`request.scope["route"].path`)으로 교체한다.
- `backend/app/utils/metrics.py`의 `cache_hit_count`/`cache_miss_count`는 정의만 있고 증가시키는 곳이 없다. `cache_store.get`에서 hit/miss를 증가시킨다(키 prefix 라벨).
- 운영 판단 자료는 기존 `http_request` duration_ms 로그(`main.py:136`)와 Sentry traces로 충분하다. Render 로그 확인 방법을 계획서에 기록한다.

## Phase 1 — 콜드 스타트 인증 (High, 프론트)
1. **토큰 동기 시드** `frontend/src/api/client.ts:16-29`: supabase-js가 저장한 `localStorage["sb-*-auth-token"]` JSON에서 `access_token`/`expires_at`을 동기로 읽는다(authStore가 이미 이 키 존재를 검사함, `authStore.ts:53`). 만료 전이면 `cachedToken`의 초기값으로 쓰고, 만료됐으면 interceptor가 getSupabase+getSession 결과를 1회 await한다(단일 promise 메모이즈). 이렇게 하면 401→refresh→재시도 왕복이 사라진다.
2. **낙관적 인증 TTL** `frontend/src/stores/authStore.ts:10,42-66`: `AUTH_ME_TTL` 30분이 지나도 sb 세션 키가 있으면 `isAuthenticated: true`로 즉시 렌더하고, `/auth/me` 검증은 백그라운드로 돌린다(실패 시 기존 로그아웃 경로). 이렇게 하면 30분 이상 만에 앱을 열 때 전체 화면 PageLoader가 사라지고, 영속 캐시가 바로 보인다. 상한(예: 7일)은 둔다.
3. **Capacitor에서 Service Worker 미등록** `frontend/vite.config.ts:51`: 네이티브에서는 `registerSW`를 건너뛴다(`injectRegister: null` + `main.tsx`에서 `!isNative()`일 때만 `virtual:pwa-register` 호출). 지금은 API 응답이 SW 5분 SWR 캐시를 거치고, 앱 업데이트 후 낡은 index.html 위험도 있다. 기존 `src/utils/platform.ts`의 네이티브 판별을 재사용한다.

## Phase 2 — 요청 폭주/불필요 요청 축소 (High~Med, 프론트)
1. **useWidget 대시보드 observer** `frontend/src/hooks/useWidget.ts:14`: 대시보드에서 `refetchOnWindowFocus: false`로 꺼둔 설정을 이 observer가 무력화한다. 위젯 갱신은 `useQuery` 대신 `queryClient.getQueryCache().subscribe`/`getQueryData`로 읽기만 하도록 바꾼다.
2. **네이티브 폴링 중지**: `useDashboardData.ts:17,25`와 `useInsights.ts:11`의 5분 폴링을 `PortfolioPage.tsx:124`과 같은 방식으로 네이티브에서 끈다.
3. **resume 버스트 완화**: `main.tsx:24`의 `refetchOnWindowFocus` 기준 60초를 5분으로 올린다. 시세성 데이터(대시보드)는 pull-to-refresh로 갱신하면 된다.
4. **accounts staleTime 통일**: observer마다 30s/1m/5m/1h로 섞여 있다(`useSelectedPortfolio.ts:30`, `useAssetManagementData.ts:16`, PortfolioManageTab 등). 공통 상수(`queryConfig.ts`의 `STALE_TIME.MEDIUM` 수준)로 맞춘다. 계좌 변경은 이미 invalidation으로 처리된다.
5. **포트폴리오 탭 자동 분석** `components/rebalancing/AnalysisPanel.tsx:69` + `useAnalysisState.ts:31-34,130-140`: 탭 진입마다 브로커 실시간 잔고(계좌 수만큼)와 analyze POST를 실행하고, 결과는 useState라 탭 전환 시 사라진다. 아래 둘을 한다.
   - 결과를 React Query(`useQuery`, key = portfolioId, staleTime 5분)로 옮겨 탭 재진입 시 재사용한다.
   - 실시간 예수금 조회는 기본값을 "스냅샷 예수금"으로 하고, 사용자가 "실시간 잔고로 다시 분석"을 눌렀을 때만 브로커를 호출한다(**사용자 확정**). 구현 전에 주문 실행 직전 단계(`plan_execution`/quick-execute)가 별도로 실시간 잔고를 쓰는지 확인한다. 쓰지 않는다면 실행 경로에서는 실시간 조회를 유지한다.
6. **투자현황 배당 waterfall/불필요 조회** `PortfolioPage.tsx:133`, `useDividendData.ts:26,37`: dividend-summary와 by-ticker(외부 API, 느림)는 배당 탭에서만 활성화하고, 기본 탭은 dividend-positions만 쓴다. overview 대기 게이트도 제거한다.
7. **홈 allocation-history** `useDashboardData.ts:57` 프리페치와 `AllocationHistoryChart.tsx:56`: 모바일 기본 접힘인데 조회와 recharts 로드가 일어난다. 프리페치를 제거하고, 카드가 펼쳐질 때만 차트 컴포넌트를 lazy mount한다.
8. **GoalTimelineCard** `GoalTimelineCard.tsx:33`: `expected_return_pct` 하나를 위해 무거운 전체 추천을 호출한다. dca-analysis나 settings 응답에 이 값이 있는지 확인하고, 없으면 백엔드 dca-analysis 응답에 기대수익률 필드를 추가한다(추천 캐시가 있으면 그 값, 없으면 기본값).

## Phase 3 — 번들/렌더 (Med, 프론트)
1. **홈 히어로 도넛** `HeroSummaryCard.tsx:9,147`: 첫 화면 카드 하나 때문에 vendor-charts(435KB)를 로드한다. 의존성 없는 인라인 SVG 도넛 컴포넌트(`components/common/` 신규, 작은 파일)로 교체한다. 그러면 홈 진입 시 recharts가 로드되지 않는다(2-7과 합쳐서).
2. **zod 분리** `vite.config.ts:37`: `vendor-utils`에서 zod를 제외해 lazy 모달과 함께 로드되게 한다(부팅 시 약 90KB 감소).
3. **Sentry 지연 초기화** `main.tsx:1`, `lib/sentry.ts`, `App.tsx:3,25`: 첫 렌더 이후 `requestIdleCallback`에서 동적 import로 init한다. **사용자 확정: 포함**. 에러 수집은 유지하고 라우터 tracing 래퍼(`withSentryReactRouterV7Routing`)는 제거해 일반 `<Routes>`를 쓴다. 에러 바운더리가 Sentry를 import하고 있다면 동적 import로 대체한다. init 전에 발생한 에러를 놓치지 않도록 `window.onerror`/`unhandledrejection`을 버퍼링했다가 init 후 `captureException`으로 넘긴다. 단독 커밋으로 둔다.
4. **모바일 이중 렌더** `StockHoldingsTable.tsx:468/520`: `hidden sm:block` 데스크톱 테이블이 모바일에서도 전 행을 렌더한다. 기존 `useMediaQuery`류 훅이 있으면 재사용해 한쪽만 렌더한다. `TransactionList.tsx:63`/`TransactionHistoryTab.tsx:268`의 모바일 카드 뷰에도 기존 데스크톱 virtualizer 패턴(`:33`, `:130`)을 적용한다.
5. **전역 리렌더** `App.tsx:60` `useMainPageFetching()`: `useIsFetching`이 AppRoutes 전체를 리렌더한다. 로딩 바를 별도 leaf 컴포넌트로 분리한다. `ExchangeRateContext.tsx:28`의 value를 `useMemo`로 감싼다. `usePullToRefresh`의 touchmove setState는 ref + rAF로 바꾼다.
6. `TacticalBacktestSection.tsx:77` `toChartSeries`와 `BacktestResultChart.tsx:121-142` 계산을 `useMemo`로 감싼다.

## Phase 4 — 백엔드 지연 (High~Med)
1. **전술 백테스트 이벤트 루프 차단** `services/tactical_backtest.py:382`: `simulate()`(일 단위 파이썬 루프 약 5,000회 × iloc)를 `await asyncio.to_thread(simulate, ...)`로 옮긴다. Render 0.1 CPU에서 수 초간 전체 사용자 요청이 멈출 수 있다. FRED 히스토리 순차 조회(`:345-375`)는 `asyncio.gather`로 병렬화한다.
2. **외부 I/O 중 DB 커넥션 점유**: `get_current_user`(`api/deps.py:50`)의 조회가 autobegin한 트랜잭션이 요청 끝까지 커넥션을 잡고 있어, 풀(5+2)이 외부 API 대기 중에 고갈된다. 대책은 두 가지다.
   - `get_current_user`에서 user 조회 직후 `await db.commit()`(읽기 전용이라 안전, `expire_on_commit` 설정 확인 필요)으로 커넥션을 반납한다. 이후 쿼리는 새로 autobegin한다.
   - 외부 I/O가 긴 엔드포인트(drift-summary, action-items, tactical GET)에서 외부 호출 전에 DB 작업을 끝내는 순서를 점검한다.
   - **위험: 중간**. expire_on_commit=True면 user 속성 접근 시 재조회 lazy-load 에러가 날 수 있다. `core/database.py`의 sessionmaker 설정을 확인하고 회귀 테스트를 둔다.
3. **get_dashboard_summary single-flight**: `/dashboard`, `/insights`, `/challenges`가 콜드 캐시에서 동시에 계산하면 배당 체인이 최대 3중으로 실행된다. 기존 `utils/inproc_lock.py` 패턴(market_signal에서 사용 중)을 `asset_aggregator.get_dashboard_summary`에 적용한다.
4. **inproc_lock 대기 상한** `utils/inproc_lock.py`: 2초(10×0.2s) 후 포기하면 각 waiter가 FRED를 개별 호출한다. 기본값을 외부 timeout(10s)보다 길게(약 15s) 올리거나 호출부별 파라미터로 둔다.
5. **drift-summary 캐시**: action-items와 drift-summary가 같은 계산(포트폴리오별 overview + market/risk)을 한 홈 로드 안에서 두 번 한다. `drift_summary_service` 결과를 user 단위로 짧은 TTL(5분) 캐시하고, 포트폴리오/계좌 변경 무효화 함수(`cache_keys.py`의 기존 `invalidate_*`)에 추가한다.
6. **기동 시 예열** (lifespan, 백그라운드 task, 실패 무시): USD/KRW 환율, market signal, technical signals. 환율 캐시가 비면 1300 하드코딩 폴백이 배당 요약(최대 24h)에 박히는 **정확성 버그**도 함께 막는다. 추가로 fallback 환율로 계산된 결과는 캐시하지 않도록 `orchestrator.py:311,318`을 수정한다.
7. **JWKS 동기 fetch** `services/auth_service.py:23-36`: `PyJWKClient`의 첫 조회가 이벤트 루프를 막는다. 예열 단계에서 `to_thread`로 미리 받아둔다.
8. **tactical tilt 실패 시 무캐시** `services/tactical_tilt.py:141`: 실패 결과도 짧은 TTL(60s, market_signal degraded와 같은 방식)로 캐시해 매 요청 재시도를 막는다.

## 범위 밖 (기록만)
- **Render 무료 플랜 슬립**: 콜드 스타트 30~60초가 가장 큰 체감 요인일 가능성이 높지만 코드 문제가 아니다. 외부 핑 서비스(UptimeRobot 등 5분 간격 `/health`)나 유료 플랜이 필요하다. 이미 계획 60 D1에 이관돼 있으며 계획서에 다시 강조한다.
- `POST /backtest/run` 전체 일별 시리즈 다운샘플링, `EXTRACT(YEAR ...)` 인덱스 비활용, 스냅샷 중복 인덱스, cache_store 전역 락은 영향이 작아 이관한다.
- DB 풀 크기 확대는 기존 결정("의도적 유지")에 따라 제외한다. 4-2로 점유 시간을 줄이는 쪽을 택한다.
